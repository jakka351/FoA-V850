# BPM Bluetooth pairing — reverse-engineering findings

Machine consolidation of the pairing R/E workflow (wf_061093cb-806), hand-cross-checked.

## Assessment

## Headless BPM pairing — can a screenless/buttonless module pair a phone?

**Short answer: Yes, but one bench session is required to call it done. The specific thing the user was worried about — the unreadable PIN — is solvable entirely from the firmware image with a one-byte flash patch.**

The problem splits into two parts. Part (b) is image-solved; part (a) has image-side options but needs a bench confirm.

### (b) The PIN problem — SOLVED from the image (directly answers "hardcode a PIN")
The 4-digit pairing passkey is **generated by the V850 host, not the Bluetooth baseband**. I disassembled the generator and confirmed every byte:

- `0x6934` (one caller only, `jarl 0x6934` at `0xdb14`) fills a RAM buffer `gp-0x6e55` (abs `0x03FFD1B7`) with 4 ASCII decimal digits from a PRNG (`0x6934 → 0x1814c`). The nibble→ASCII step is at **file offset `0x69a0`: `0b 56 30 00` = `addi 0x30, r11, r10`** (verified by objdump and by the raw bytes).
- That **same buffer is used twice**: it is painted on the dash (painter reads `movea -0x6e55,gp,r7` at `0x1b93a`) **and** pushed to the baseband as the pairing PIN. Right after generation, `0xdb1c-0xdb22` does `mov 0x4,r6 / movea -0x6e55,gp,r7 / jarl 0x68c8`, and `0x68c8` builds a baseband message `[opcode=0x03, seq, len=4, d0..d3]` (`mov 0x3,r10; st.b r10,-0x7ae4[gp]` at `0x68de`, payload copy loop `0x68f6-0x691a`) and dispatches it.

Because the host both **shows** and **sends** the PIN from one buffer, pinning that buffer to a constant fixes the real pairing PIN end-to-end, and the installer knows it in advance — no screen needed.

**Exact patch (PIN = 0000):** file offset **`0x69a0`, change byte `0x0B` → `0x20`**. This turns `addi 0x30,r11,r10` (`0b 56 30 00`) into `movea 0x30,r0,r10` (`20 56 30 00`), forcing every emitted digit to `'0'`. The result is byte-length-identical (both 4-byte, no realignment) and is the *same encoding* already present at `0x16e24` (`20 56 30 00 = movea 0x30,r0,r10`), so it is a known-valid instruction. Then re-checksum/re-wrap the PHF with the repo's existing pipeline (`build_spp_can_phf.py` / `phfpatch.py`; stock FILE CHECKSUM 0xE5C3 is reproduced by `phf2bin.py`).

**For any other PIN (e.g. 1234):** `0x6934` has exactly one caller, so repoint `jarl 0x6934` at `0xdb14` to a ~20-byte stub in free flash (`0x1EB68`, a verified contiguous 0xFF run of 127,896 bytes to `0x3DF00`) that writes the 4 chosen ASCII bytes + NUL into `gp-0x6e55` and returns `r29=1`.

### (a) The trigger problem — image-side options, bench to finish
The module does **not** auto-enter discoverable on an empty phone list (boot shows the passive "No Phone Paired"/"Please pair a new phone" screen and issues no discoverable command), so pairing must be triggered. Three routes:
1. **Firmware auto-trigger (cleanest, mostly image-derivable):** call `0x19D8C` with `r6=1`, which does `set1 0x1,-0x611c[gp]` (bit1 = PAIR; verified at `0x19d9a`). The BT task's executor (`tst1 0x1,-0x611c` at `0x1a8aa`) then issues the module's *own* baseband PAIR command — so you reuse the firmware's discoverable path without knowing the raw baseband opcode or injecting any CAN. A small patch drives this once when unpaired.
2. **CAN injection:** the select/OK event is image-proven (ID `0x2E2`, data byte0 bits[2:0]==4; handlers `0x1B694/0x1B6D2/0x1B6F8`), and a power keepalive on `0x406` byte1 (value 2/4/8) keeps BT alive. But the full stateful "navigate to Phone menu → highlight PAIR A NEW PHONE → OK" frame sequence on `0x2CF/0x2CD/0x2C1` is **not** statically derivable → bench capture.
3. **Direct baseband discoverable command** over the UART (candidate opcode `0x2b`) → needs the baseband opcode confirmed.

### The real crux (bench): SSP vs legacy PIN
Whether a modern phone actually uses the host-supplied 4-digit PIN depends on the **baseband's** RF pairing negotiation, which is **not in `bpm.bin`** (no baseband part/config, no AT/CSR strings). The firmware implements the legacy **BT 2.0 "car supplies PIN"** model (host generates digits, sends them via opcode 3, and verifies the phone's echo at compare routine `0x7832`, which auto-advances to "Paired successfully" with no dash button). For a 2008 HFP baseband this is the likely path and the hardcode is the correct bet. But if the baseband negotiates **BT 2.1 SSP** (numeric comparison / Just Works), the host PIN is bypassed and the headless fix instead becomes "auto-accept the compare event" (handler `0x7832` / event `0xb7`). This single question must be answered against a real phone.

### Reconciling the four readers
Three readers proved the host-side generator and the hardcode. The fourth ("can-hmi-map") reported "no hardcoded PIN in the image" — literally true (there is no constant PIN *string*, and the painter's placeholder at `0x4e3b` is an empty string), but it examined only the CAN/HMI/string surface and did not disassemble `0x6934`, where the PIN is produced *by code*. That code is patchable to a constant, which that reader also acknowledged as the firmware route. No real contradiction: all four reconcile.

### Fit with the existing bridge
The shipped `8R29-14D511-JL-SPPCAN.PHF` keeps the HFP stack intact and injects its shim at `0x1EB68` with 4 hook sites — none of which is `0x69a0`. The PIN patch is therefore an independent, compatible change; the only build-side step is whitelisting `0x69a0` (and any trigger patch) in the builder's "only-these-bytes-changed" verify step.

## Per-reader facts

### BPM Bluetooth pairing — passkey/PIN generation model and headless hardcode patch
The pairing passkey is a RANDOM, per-session 4-digit decimal PIN generated in software by the V850 (xorshift PRNG), stored in one RAM buffer (gp-0x6E55, 4 ASCII bytes + null). That same buffer is BOTH displayed on the FDIM pairing screen AND pushed to the Bluetooth baseband as the PIN to use. The model is legacy Bluetooth 2.0 "car generates+shows a PIN, user types it into the phone" — NOT an SSP "phone shows a code, confirm on the car" model. The car-side compare (0x7832) checks digits reported back by the baseband against the stored PIN and auto-advances to "Paired successfully" with no dash-button gate. This is exactly the user's problem: with no FDIM screen the random PIN is unreadable, so pairing is impossible as shipped. FIX: because the PIN lives in one buffer that is both shown and sent to the baseband, a single-byte flash patch at file offset 0x69a0 (0x0B -> 0x20) pins the PIN to "0000"; pairing then completes entirely phone-side (enter 0000 on the phone), needing no screen and no CAN OK-button injection.

- [image-proven] The passkey shown on the pairing screen is a RAM string at gp-0x6E55 (the "passkey buffer"), not a flash constant.  (0x1b938)
- [image-proven] The line at string address 0x4E3B that the FIRST painter variant puts under "Enter passkey" is an EMPTY string (a blank placeholder), not the PIN.  (0x4e3b)
- [image-proven] The line-formatter 0x1B0E0 is a plain character copy with per-line stride 0x44 and a per-line attribute byte at +0x43 — it does NO number-to-ASCII synthesis, so the displayed passkey is literally whatever is in gp-0x6E55.  (0x1b0e0)
- [image-proven] The passkey buffer gp-0x6E55 is filled with 4 random DECIMAL digits by helper 0x6934, which is called from exactly one site and is dedicated to the PIN.  (0x6934)
- [image-proven] The digit source 0x1814c is a software xorshift PRNG, so the passkey is RANDOM / per-session, generated locally by the V850 — it is neither a fixed constant nor received from the baseband.  (0x1814c)
- [image-proven] After generating the PIN, the V850 SENDS the 4 digits to the Bluetooth baseband (so the baseband pairs with this exact PIN), then displays it and starts a timer.  (0x68c8)

### BPM Bluetooth pairing / discoverable-mode state machine and passkey (PIN) handling
Pairing in the FG Falcon BPM is a THREE-party flow: (1) the Bluetooth baseband owns the pairing RF state, (2) the V850 host owns the 4-digit passkey AND renders screens, (3) the FDIM delivers menu/button events over MS-CAN. There is NO single host "pairing mode" flag the firmware sets to start pairing; instead the host pairing-PHASE byte gp-0x6e57 (phys 0x03FFD1B5, values 0..6) is written EXCLUSIVELY from the baseband's 16-bit status word (top nibble -> switch at 0x7936), and when it is 0/1 the HMI renders screen code 0 = painter 0x1B848 "PAIR A NEW PHONE / Bluetooth active / Enter passkey". The module does NOT auto-enter pairing on an empty phone list: boot (0x6020-0x60C8) sets gp-0x6e57=0, inits the 8 paired-phone records at gp-0x7a5c to "Empty", and sends NO discoverable command; with no phone it only shows the passive "No Phone Paired / Please pair a new phone" screen (code 0x25, painter 0x1D6A2). Pairing is entered by an explicit user action: the FDIM "PAIR A NEW PHONE" menu selection arrives as CAN HMI frames on IDs 0x2CF/0x2CD/0x2C1 (+own 0x781) -> extractor 0xF77E -> HMI interpreter 0x16324/0x16BC8, which drives the host to send a "become discoverable" command to the baseband (one of ~27 opcode wrappers at 0x6840-0x6EC8 that call sender 0x18F08). CRITICAL for the user's "hardcode a PIN" idea: the 4-digit passkey is GENERATED BY THE V850 HOST (pseudo-random, routine 0x6934), stored as 4 ASCII digits at gp-0x6e55 (phys 0x03FFD1B7), DISPLAYED on the dash (painter line at 0x1B93A) AND SENT to the baseband as command opcode 3 (0x68C8 -> 0x18F08). So the host is the PIN authority -- a fixed PIN can be hardcoded by patching 0x6934, and/or the running SPP-CAN bridge can simply read gp-0x6e55 and relay the live PIN.

### FG Falcon BPM host↔Bluetooth-baseband UART (UARTA1) pairing protocol — framing, opcodes, PIN generation, headless feasibility
The V850↔baseband link is a framed binary protocol over UARTA1, NOT ASCII/AT. The UART ISRs are a transparent byte pipe (two 300-byte rings); the real protocol framer is the state machine at 0x7060 (state at gp-0x7fef), and a completed frame is dispatched by 0x7314. Wire frame = 0xC0 | opcode | seq | len | payload[len] | cksum_hi | cksum_lo | 0xC0, with 0x7E as the escape (literal 0xC0/0x7E are sent as 0x7E followed by byte^0x20), a rolling seq byte, and a 16-bit two's-complement checksum over opcode+seq+len+payload (so the total sum ≡ 0). Direction is encoded in bit7 of the opcode: host→baseband commands are 0x01–0x49, baseband→host responses/events are command|0x80 (0x81–0xFF). CRITICAL for the user's concern: the 4-digit pairing passkey is NOT fixed — it is generated host-side by routine 0x6936 using an xorshift128 PRNG (0x1814c, constant 0x9D2C5680) seeded from a free-running tick counter (gp-0x7f78), written to RAM buffer gp-0x6e55 (0x03FFD1B7), shown on the dash (painter 0x1b8d4), AND pushed to the baseband as the PIN via command opcode 0x03. Because the host both generates and transmits the PIN, hardcoding a fixed PIN is feasible: patch the 172-byte generator at 0x6936 to store constant ASCII digits. The stock random PIN is genuinely unknowable without the FDIM screen, confirming the user's worry.

- [image-proven] The UARTA1 ISR layer is a transparent byte pipe, not a protocol framer. gp-0x6533 (task premise's 'framer state') is only RX-ring flow-control: 2=ring-full/drop, 3=ring-empty, 4=byte-stored. The actual protocol framer is a separate state machine at 0x7060 using state byte gp-0x7fef.  (0x17c54 / 0x7060)
- [image-proven] Wire frame structure = 0xC0(start) | opcode | seq | len | payload[len] | cksum_hi | cksum_lo | 0xC0(end). Delimiter byte is 0xC0.  (0x19040 (TX) / 0x7082 (RX states))
- [image-proven] Byte-stuffing: escape char is 0x7E. Any payload or checksum byte equal to 0xC0 or 0x7E is transmitted as 0x7E followed by (byte XOR 0x20); the receiver reverses this (next byte XOR 0x20).  (0x190ec / 0x7196 / 0x6784)
- [image-proven] Checksum is a 16-bit two's-complement sum of (opcode+seq+len+payload) so that (opcode+seq+len+payload+checksum) & 0xFFFF == 0. It is appended as hi,lo and is itself subject to 0x7E escaping.  (0x19192 / 0x7282)
- [image-proven] seq (2nd header byte) is a rolling counter 0..0x50 (wraps at 0x51) produced by 0x6748; it is not validated on RX (only summed into the checksum).  (0x6748)

### FG Falcon BPM (V850ES) — CAN FDIM→BPM button/HMI event map and the pairing-trigger path, for driving the headless BPM over CAN
The BPM is a display/HMI slave. It RENDERS its screens itself (painter table, switch @0x1DA8A, 43 screen-ids; screen 0 = the "PAIR A NEW PHONE/Enter passkey" screen at 0x1B842) and RECEIVES input from the FDIM over MS-CAN. Of the 9 accepted RX IDs, the ID that carries FDIM button/select events is 0x2E2: every per-screen input handler reads 0x2E2 data byte0 bits[2:0] as a 3-bit event code and acts on code 4 (select/OK/press); press-vs-hold is resolved by firmware debounce timers (matches the "Press button"/"Hold button" strings). 0x406 is NOT buttons — its byte1 bits[4:0] is the vehicle ignition/power-mode (values 2/4/8 = powered) that gates BT power/shutdown. A richer structured FDIM<->BPM command/status channel exists as RX 0x2CD/0x2CF/0x2C1 (parsed by 0x16324, validated via table @0x4A9C) paired with BPM TX 0x2CC/0x2CE; BPM pushes display content on TX 0x789/0x541/0x2E3/0x2E1. Selecting a BT menu action sets a command bit in gp-0x611c (bit1 = PAIR, descriptor @0x4DD0) which 0x19758/0x1A8xx issues to the Bluetooth baseband over UART. CRITICAL for the user's concern: there is NO hardcoded PIN anywhere in the image and the PAIR screen's passkey line (0x4E3B) is empty in flash — the BPM uses SSP with a passkey generated at pair time and shown on the dash, so headless you can neither see nor preset it without changing the baseband's pairing mode (UART side, bench).

- [image-proven] The 9 RX-accepted std IDs map to internal type-codes via parallel flash tables: IDs @0x48F8 (pre-shifted MIDH) and type-codes @0x490A. Order: buf21 0x781->t5, buf22 0x406->t0, buf23 0x317->t1, buf24 0x2FC->t2, buf25 0x2F2->t3, buf26 0x2E2->t4, buf27 0x2CF->t6, buf28 0x2CD->t7, buf29 0x2C1->t8.  (0xF77E / tables 0x48F8,0x490A)
- [image-proven] Per type-code, the extractor copies the frame into a RAM mailbox (ptr table @0x4928) and runs a decode handler (jump table @0x494C) and an action/notify handler (table @0x4970). Min-DLC per type is table @0x491C = [0x406:2, 0x317:8, 0x2FC:5, 0x2F2:7, 0x2E2:2]; a frame is rejected if its MDLC is below this.  (0xF80C / tables 0x4928,0x4970,0x491C)
- [image-proven] ID 0x2E2 is the FDIM->BPM button/select event frame. The event code is CAN data byte 0, bits [2:0]. The value 4 is the select/OK/activate event — it is the one value every BPM screen input-handler special-cases; all other codes route to a common 'button-down/idle' path.  (0x1B498,0x1B4C2,0x1B500,0x1B532,0x1B694,0x1B6D2,0x1B6F8)
- [image-proven] Only byte0[2:0] of 0x2E2 is ever read — no other bits/bytes. So 0x2E2 is a pure small-event frame (a shared ICC/steering-wheel button enum); the BPM reacts to one value (4). This means the BPM itself does not scroll menus from 0x2E2; press-vs-hold is derived from firmware tick-timers, not extra codes.  (0x15F40 (timer) / all 0x6840 reads)
- [likely] ID 0x406 is NOT buttons — its field is CAN data byte1 bits[4:0] and behaves as the vehicle ignition/power-mode (powered values 2/4/8). It gates BT power/display behaviour (the 'Disconnected - low car battery' / 'Bluetooth shutting down' strings).  (0xC3F0-0xC4B0, 0x13A5A-0x13A7C)
- [image-proven] The BPM transmits its display content and a command/response channel, confirming a master(FDIM)/slave(BPM) HMI: BPM TX IDs (table @0x4850, value>>2) = 0x789,0x541,0x2E3,0x2E1 (menu/media/list/text to FDIM) and 0x2CE,0x2CC (responses). RX 0x2CD/0x2CF/0x2C1 form the inbound half of a structured command/status channel parsed by 0x16324 and validated against opcode table @0x4A9C.  (0x4850 / 0x16324 / 0x10EB4 / 0x4A9C)
- [image-proven] The BPM paints its own screens from a 43-entry painter jump (switch @0x1DA8A on screen-id in r11). Screen 0 = the active-pairing screen (header 'PAIR A NEW PHONE' 0x4E08 + 'Bluetooth active' + 'Enter passkey'), painter at 0x1B842/0x1B848 via line-formatter 0x1B0E0 into gp-0x58E8. Screens 1-5 are the other pairing sub-states; screen 11 = DELETE-confirm; screen 37 = 'No Phone Paired'.  (0x1DA8A / 0x1B842)
- [image-proven] Selecting a BT menu function sets a command bit in gp-0x611c and 0x19758/0x1A8AA issues it to the baseband. bit1=PAIR (descriptor @0x4DD0), bit2/3/4 = the other 3 functions (connect/disconnect/delete, descriptors @0x4DD4/0x4DD8/0x4DDC). The pair bit is set by the BT task at 0x19BA0/0x19C6E (mov 0x1,r6; jarl 0x19D8C -> set1 0x1,gp-0x611c).  (0x19D8C,0x1A8AA,0x4DD0,0x4DE0)
- [image-proven] There is NO hardcoded Bluetooth PIN in the image, and the PAIR screen's passkey/value line (string 0x4E3B) is an empty string in flash. The BPM therefore uses SSP with a passkey generated at pairing time and shown on the dash — there is nothing in firmware to read or preset as a fixed PIN.  (0x4E3B / 0x1B8AE)
- [bench-needed] The CAN->pairing linkage is mediated by a cooperative-scheduler BT task (CALLT coroutines around 0x19B82) and the baseband UART protocol; the structured command channel (0x2CD/0x2CF/0x2C1 via 0x16324) does not itself write gp-0x611c or the screen state. So a single 'this exact frame = start pairing' CAN message is not statically pin-pointable from the image alone.  (0x19B82 / 0x16324 sub-handlers)
